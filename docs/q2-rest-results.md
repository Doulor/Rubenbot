## 1. 真语音转写（`fetch_ptt_text` `ptt translate failed: error=9`）

### 结论

**FAIL，根因在上游（QQ 转写服务），不是本侧入参、消息段格式或编解码问题。** 本侧不改代码硬绕；已把实测边界写进文档，并保留「原生转写必须由 HTTP 后端兜底」的既有设计。

### 实锤证据

1. **自聊合成语音（flite TTS → WAV，1 秒 / 2.6 秒 / 3 秒三种，经 `base64://` 与 `data:` URL 两种内联方式发送）：**
   发送均 `status=ok`，`get_msg` 读回 `record` 段，`get_record` 能正常取到文件（`file_name`、`file_size` 正常）——说明消息、媒体缓存、下载链路都通。
   紧接着 `fetch_ptt_text` 返回 `status=failed, retcode=100, wording=ptt translate failed: error=9`。同一消息重试结果一致（1.2 秒出结果，不是超时）。
2. **协议端自己的日志（只读）：** `ptt translate errCode=9 isGroup=false md5=16B format=1 uuid=set dur=3 size=10382`。请求包字段齐全（md5 完整、uuid 有值、时长与大小真实），失败发生在 QQ 服务端回包。
3. **同一账号、同一协议端的历史群语音对照（只读，未发送）：** 13 个群历史里共 5 条语音，逐条转写：

   | 语音年龄 | 结果 |
   |---|---|
   | 33.6 小时 | 成功，返回 200 字 |
   | 67.5 小时 | 成功，返回 208 字 |
   | 15.5 小时 | 失败：20 秒内未收到结果推送 |
   | 56 天 | 失败：20 秒内未收到结果推送 |
   | 70 天 | 失败：20 秒内未收到结果推送 |

   另一次扫到两条群语音返回 `errCode=4294966146` / `4294966162`（按 32 位有符号解读为 -1150 / -1134）。**同样的调用方式，有的语音能转、有的不能**，失败与「谁发的」「入参形状」无关，而与语音本身在上游的状态有关。
4. **对外部实现核对：** 该版本的 `fetch_ptt_text` 由 SnowLuma 发 `pttTrans.TransC2CPttReq` 等原始包，错误码原样抛自 QQ 服务端回包；协议端不提供可绕过的本地转写。

### 判定：本侧无可修

- 入参只有一个 `message_id`，无需额外字段；消息能读回、语音能下载，排除「消息不存在/缓存缺失」这类本侧错误。
- 同一消息重复请求返回相同错误码、1.2 秒返回（不是 20 秒等待超时），排除重试参数问题。
- 本分支不改网关去伪造文本、不把失败包装成空串冒充成功；`VoiceService` 按既有设计顺延到 HTTP 后端，全失败留 `[语音]` 占位。

### 还缺什么条件

- **要让它稳定可用，必须另配一个 HTTP 转写后端**（`siliconflow` 或 `openai_compatible` + key）。线上当前 `voice.stt_provider: qq_native`、其余后端未配置，所以线上遇到这类语音时只会留 `[语音]` 占位。这需要机主提供一个 STT 服务的 key/地址，**属于机主侧配置决定，本任务不擅自改线上配置**。
- 若要继续追 QQ 服务端为什么对部分语音返回 error=9，需要 QQ 侧文档或官方答复，超出本仓库范围。

## 2. 表情包实发

### 结论

**私聊/自聊：PASS（修复后）。群内贴表情（`set_msg_emoji_like`）：未验，等机主提供专用测试群。**

### 发现并修复的产品缺陷

线上 `7b8c574` 的 SnowLuma 表情发送路径在真机上**发不出去**，原因有两层，都属于本侧可修：

1. **QQ 多媒体 URL 不可复用**：表情库里 `native_refs.snowluma` 对「图片段」存的是 QQ 下载链接。把该链接交给协议端去自己下载，实测返回 `HTTP download failed: 400`；带原始 `rkey`、去掉查询串、只留 `fileid` 三种形式都试过，全部 400（rkey 是一次性的/绑定会话）。
2. **本地路径协议端读不到**：SnowLuma 在容器里，bot 在主机上；传 `/tmp/xxx.png` 返回 `ENOENT: no such file or directory`。这个问题同样影响**语音发送**（`message.voice`）和**电脑工具附件**（`send_file`），此前实现都是「写临时文件、把路径交给协议端」。

修复（本分支）：三处出站媒体一律改为 **`base64://` 内联字节**；表情图片段优先用表情库里的本地本体（保留 `summary` 等描述字段），本地没有本体才退回 URL。`mface` 原生表情段不受影响。

### 实锤证据

- **修复前（线上代码路径）**：真实表情库条目 `call_capability(send_sticker)` 两次均失败，错误为 `OneBot API send_private_msg 失败`（上游 `HTTP download failed: 400`）。
- **修复后（本分支代码，临时 overlay）**：同一批真实表情库条目 `send_sticker` 自聊实发返回 `status=ok` 与 `message_id`；`get_msg` 读回段类型 `image`；`delete_msg` 撤回成功。另用库内 102 KB / 2.1 MB / 2.2 MB / 4.5 MB 的真实图片（含 GIF 动图）直接内联发送，均成功并撤回——大小不是边界。
- **语音出站**：修复后 `message.voice` 自聊发送成功、读回 `record` 段、撤回；修复前同一调用报 `ENOENT`。
- **附件**：修复后 `send_file` 自聊发布成功，`get_friend_msg_history` 读回 `file` 段（`q2-branch.txt` / `q2-probe2.txt`），按名匹配后撤回。

### 群内贴表情为什么仍未验

`set_msg_emoji_like` 只支持带 QQ 权威序号的**群消息**；私聊返回 `not supported`（`7b8c574` 已记录）。小号所在的 13 个群全是真人群（最小 7 人），没有专用测试群；按纪律**不在主群或任何真人群贴表情**，所以不做。

**等机主提供**：一个非主群的专用测试群 + 该群里一条小号发的真实消息（或授权小号在测试群发一条再贴），才能在客户端核对表情效果。

## 3. web_search 查证链

### 结论

**PASS（修复一处产品缺陷后）。** 搜索渠道、公网抓页、只读摘录、出站引用四段真机走通；`verified_pages_read` 置位、出站为带来源 URL 的原句。

### 发现并修复的产品缺陷

线上 `7b8c574` 的 `web_search` 在真实资讯站上**几乎总是查不到原文**：`computer_fetch._body` 对压缩正文调用 `read_compressed_body` 时，只要解压后超过 256 KiB 就抛 `CompressedBodyError('正文过大')`，整页放弃。实测前两条 Tavily 结果（新浪财经 96 KB、凤凰网 35 KB **解压后**）都被判「正文过大」，于是每轮 0 句原文，必然回「没查到能回答这个问题的原文」。这与「每页最多读入 8 KiB」的设计意图矛盾：本来就是要截断读前段。

修复（本分支）：`read_compressed_body` 增加 `allow_truncated`，抓页路径解到额度即截断、由 `_body` 补 `[已截断]`；链接插件与表情下载等需要完整正文的路径保持原来的报错语义。未支持编码、损坏/截断压缩流仍报错。

### 实锤证据

- **修复前（线上代码）**：同一提问下 Tavily 命中 5 条 → 前两页 `CompressedBodyError 正文过大` → `verified_pages_read=False` → 出站 `没查到能回答这个问题的原文，我还不确定。`
- **修复后（本分支代码，临时 overlay）**：新浪 140 字、凤凰 667 字（均标截断），`verified_pages_read=True`，出站为原句加来源：
  > 原文写的是：「中国人民银行授权全国银行间同业拆借中心公布，2026年11月20日，贷款市场报价利率（LPR）为：1年期LPR为3.00%，5年期以上LPR为3.50%，均较上月保持不变……」 · https://feng.ifeng.com/c/8yCUracESD7
- **模型自主选择全链**：线上配置模型（走线上运行时密钥、独立进程、隔离库、Console 适配器不发真机）在一次提问里自主选择 `web_search`，参数 `{"query": "2026年11月20日 LPR报价 1年期 5年期", "count": 5}`，命中 Tavily、读到原文、出站带出处，`verified_pages_read=True`。这次调用证明「模型决策 → 搜索 → 抓页 → 摘录 → 出站」整链可用。
- 对照（不作为受控 A/B）：同一提问在**未修复**的线上代码上，模型没有给出带原文的回答（回「那天还没到」）。模型是否选择搜索、选哪个检索词每次会有波动，因此只把它记为一致方向的旁证，不把差异全部归因于抓页修复；抓页这一环的差异本身已由上面的单点复现（同 URL 修复前报错、修复后读到正文）直接证明。

### 需要写清的限制

- 模型不总是主动选择 `web_search`：换措辞问「最近一周量子计算进展」时它选择直接答/认不知道。这是模型行为，不是链路故障。
- 防私密外泄的硬门仍在：模型给出的检索词必须原样出现在**用户本轮原话**里，否则直接回「没查实」。例如用户说「最近一周有什么量子计算进展」，模型给 `量子计算 重要进展 本周`（「本周」不在原话里）就会被拦。这是既有安全设计，**未改动**；实测中它确实会拦掉一部分本可查证的问题，属于可预期的取舍。
- Tavily key 在线上 config 中存在且可用；`deepseek` 渠道未配 key，链上会被跳过。计费：本任务消耗了若干次 Tavily / 模型调用（手动实测，非 pytest）。

## 4. 提醒到点触发

### 结论

**PASS（隔离库 + 真实 SnowLuma 适配器，投递到自聊）。** 没有碰生产库、没有投给机主或任何群。

### 实锤证据

- 用线上配置（`database_path` 改成临时文件、WebUI 关、`reply.max_segments=1`）+ 真实 SnowLuma 适配器，`bot.set_reminder({"delay_minutes": 0.05})` 写入 `scheduled_jobs`（`fire_in_s=3.0`）。
- `Scheduler.run` 按 2 秒间隔扫描：`pending → pending → done`，`fired_at` 非空，库表行 `(1, 'done', 1)`。
- 日志：`设置提醒 #1：snowluma/3657338908 …` → `提醒 #1 已发送：…`；生成正常时由模型按提醒正文现写一句（首轮曾因独立进程取不到线上密钥报 401，此时退回提醒原文照常投递——这是既有的降级路径，不是缺陷）。
- 投递：适配器台账记录 `('3657338908', 'private', <message_id>, ['text'])`；按 id `get_msg` 读回正文（16 字），`delete_msg` 撤回成功。临时 SQLite 用完删除。

### 限制

- 这是「隔离库 + 真实协议端」的到点验证，不是线上生产库里的提醒（按纪律不写生产库）。线上调度器是同一份代码，靠同一张 `scheduled_jobs` 表工作；**生产环境到点投递未单独观察**，因为要写生产库、需要机主侧操作。若要线上验收：机主只需在私聊里让 bot 设一条几分钟后的提醒，观察 `bot.log` 的 `提醒 #N 已发送`。
- 迟到（>1 小时）路径、进程重启后的补发由既有 pytest 覆盖，本次没有真机制造进程中断。

### 清理残留在自聊（未删掉，如实记录）

- 自聊历史里仍有 3 条本轮测试消息：一张表情图片（05:31）、两条提醒文本（06:05，生成句为「嘿，忙归忙，」与「先喝口水吧。」）。对它们再次 `delete_msg` 返回 `status=ok`，但 1 秒后 `get_msg` 仍是 `ok`；用一条新消息做对照（发送→1 秒内撤回）则 `get_msg` 返回 `message not found`。**结论：这些消息已超出 QQ 的撤回时限（约 2 分钟），协议端回执成功但上游不执行撤回。** 它们只留在小号自己的私聊里，不涉及任何真人或群；如需彻底清掉，只能由机主在小号的 QQ 客户端手动删除（本任务没有客户端操作能力）。
